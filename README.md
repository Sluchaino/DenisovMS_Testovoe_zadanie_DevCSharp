# ДенисовМ.С._Тестовое задание_DevC#

Vulnerability Tracker API — REST API на ASP.NET Core (.NET 10).
Автор: Денисов М.С.

Репозиторий: https://github.com/Sluchaino/DenisovMS_Testovoe_zadanie_DevCSharp

Сервис предоставляет операции создания и получения уязвимостей, запуск фоновых задач сканирования, получение их состояния и результата. Реализованы оба дополнительных требования: настраиваемое ограничение параллельности с очередью и отмена ожидающих/работающих задач. Всё состояние хранится в памяти и сбрасывается после перезапуска.

## Сканирование

Сканирование реализовано как **имитация длительной операции с демонстрационным результатом**. Поддерживаются очередь, ограничение параллельности и отмена.

По умолчанию задача проходит 10 отменяемых шагов по 1 секунде, затем возвращает один фиксированный пример находки с `isSimulation: true`. Значения не зависят от URL или содержимого репозитория. Репозиторий не скачивается, его существование и доступность не проверяются, исходники не анализируются. Для запуска задачи передаётся HTTP(S) URL репозитория. Демонстрационный результат не является оценкой безопасности кода и автоматически не добавляется в реестр `/vulnerabilities`.

## Запуск

Требуется .NET SDK 10.0.x. Для работы сервиса Git, Docker, база данных и внешние анализаторы не нужны. Из корня репозитория:

```sh
dotnet restore VulnerabilityTracker.slnx
dotnet build VulnerabilityTracker.slnx --configuration Release
dotnet run --project src/VulnerabilityTracker.Api
```

- API: http://localhost:5080
- Swagger UI: http://localhost:5080/swagger
- OpenAPI JSON: http://localhost:5080/openapi/v1.json

Остановка: Ctrl+C. Сервис прекращает приём задач и отменяет активные и ожидающие задачи. При запуске с `--no-launch-profile` адрес задаётся через `--urls` или `ASPNETCORE_URLS`. Swagger доступен во всех окружениях для удобства проверки задания.

## Эндпоинты

| Метод и маршрут | Результат |
| --- | --- |
| `POST /vulnerabilities` | `201 Created`, запись с ID и датой, заголовок Location |
| `GET /vulnerabilities/{id}` | `200 OK`, полная запись; `404` для неизвестного ID |
| `POST /scans` | `202 Accepted`, ID и исходное состояние задачи, Location |
| `GET /scans/{id}` | `200 OK`, состояние, даты, результат/ошибка; `404` для неизвестного ID |
| `POST /scans/{id}/cancel` | `200 OK`, ID, время запроса отмены, success и статус; `404` для неизвестного ID |

ID — GUID, даты — UTC/ISO 8601. Критичность задаётся строкой: `Low`, `Medium`, `High`, `Critical`. Название обязательно, не только пробелы, максимум 200 символов. URL должен быть абсолютным HTTP(S), до 2048 символов, без встроенных учётных данных.

Некорректные данные возвращают `400 ValidationProblemDetails`. Полная/закрытая очередь — `503` без сохранения задачи. Необработанная HTTP-ошибка — `500 ProblemDetails` с traceId без подробностей исключения. Исключение сканера переводит его задачу в `Failed`, обработчик продолжает работу. Случайные ошибки в имитацию не добавлены; этот сценарий проверяется управляемым тестовым сканером.

## Примеры запросов

PowerShell:

```powershell
$vulnerability = Invoke-RestMethod http://localhost:5080/vulnerabilities -Method Post -ContentType 'application/json' -Body '{"name":"SQL injection","severity":"Critical"}'
Invoke-RestMethod "http://localhost:5080/vulnerabilities/$($vulnerability.id)"

$scan = Invoke-RestMethod http://localhost:5080/scans -Method Post -ContentType 'application/json' -Body '{"repositoryUrl":"https://gitlab.com/example/project"}'
Invoke-RestMethod "http://localhost:5080/scans/$($scan.id)"
# Для проверки отмены до окончания задачи:
Invoke-RestMethod "http://localhost:5080/scans/$($scan.id)/cancel" -Method Post
```

Bash:

```sh
curl -i http://localhost:5080/scans \
  -H 'Content-Type: application/json' \
  -d '{"repositoryUrl":"https://gitlab.com/example/project"}'
curl http://localhost:5080/scans/ВСТАВЬТЕ_ID
curl -X POST http://localhost:5080/scans/ВСТАВЬТЕ_ID/cancel
```

Поле result завершённой задачи:

```json
{
  "isSimulation": true,
  "findings": [
    {
      "name": "Demonstration vulnerability",
      "severity": "High",
      "file": "demo/example.txt",
      "line": 1
    }
  ]
}
```

Путь и строка в этом примере вымышлены. До завершения задачи result равен null.

## Очередь и отмена

```text
Queued -> Running -> Completed
                  -> Failed
Queued  -> Cancelled
Running -> Cancelled
```

`ScanService` использует ограниченный `Channel<ScanJob>` и фиксированное число обработчиков. Каждый обработчик ждёт завершения одной задачи, прежде чем получить следующую. Брокер сообщений не требуется для однопроцессного сервиса с непостоянным состоянием.

Отмена сразу переводит задачу в `Cancelled`, передаёт сигнал сканеру и прерывает текущий `Task.Delay`. Место обработчика освобождается после выхода сканера. Ожидающая отменённая задача остаётся в канале до получения обработчиком, который её пропускает; до этого она занимает место в очереди.

Пример ответа отмены:

```json
{
  "id": "8b065e62-4965-4daa-92c0-2321ac3930dd",
  "time": "2026-11-04T12:00:00+00:00",
  "success": true,
  "status": "Cancelled"
}
```

Повторная отмена и отмена Completed/Failed возвращают `success: false`, не меняя дату состояния. Если отмена и завершение совпадают, побеждает первый переход под блокировкой. Терминальное состояние не меняется. Статус, дата и результат обновляются вместе и возвращаются неизменяемым снимком.

## Настройки

Файл: `src/VulnerabilityTracker.Api/appsettings.json`. Настройки проверяются при запуске, изменения применяются после перезапуска.

| Секция и параметр | По умолчанию | Диапазон | Назначение |
| --- | --- | --- | --- |
| Scanning:MaxParallelScans | 2 | 1–32 | Число фоновых обработчиков |
| Scanning:QueueCapacity | 100 | 1–10000 | Вместимость ожидающей очереди |
| Simulation:SimulationSteps | 10 | 1–100 | Число шагов имитации |
| Simulation:StepDelayMilliseconds | 1000 | 1–60000 | Задержка одного шага, мс |

Можно переопределять переменными окружения, например `Scanning__MaxParallelScans=1`. Чтобы увидеть очередь вручную, установите один обработчик и отправьте несколько сканирований подряд: первое станет Running, следующие — Queued. Можно отменить как ожидающую, так и работающую задачу. Длительность имитации приблизительно равна числу шагов, умноженному на задержку шага.

## Файлы и логирование

- `src/VulnerabilityTracker.Api` — API, модели, хранилище, имитация сканирования, очередь и обработка ошибок.
- `tests/VulnerabilityTracker.Tests` — unit-тесты и HTTP integration-тесты через WebApplicationFactory.
- `.github/workflows/ci.yml` — сборка и тесты GitHub Actions на Linux.
- Репозитории не скачиваются; временных копий, базы и файлов результатов нет.
- Логи выводятся в консоль. HTTP Logging фиксирует метод, путь, код ответа и длительность. Тела, заголовки и query string в HTTP-лог не включены.
- Переходы и ошибки фоновых задач логируются с ID задачи. Подробности ошибок остаются в логах сервера.
- Артефакты сборки находятся в bin/ и obj/ проектов и исключены из Git.

История задач и уязвимости хранятся до остановки процесса. Очередь ограничена, автоматического удаления истории нет. Сервис рассчитан на один экземпляр приложения.

## Тесты

```sh
dotnet test VulnerabilityTracker.slnx --configuration Release
```

Проверяются создание/чтение, валидация и ошибки HTTP, OpenAPI/Swagger, сброс хранилища, лимит параллельности, заполненная очередь, отмена ожидающих и активных задач, повторная отмена, гонка завершения с отменой, ошибка сканера и остановка сервиса. HTTP-тесты используют зарегистрированную в приложении имитацию с уменьшенной задержкой; сеть не требуется. Ссылки на разные хостинги возвращают явно помеченный демонстрационный результат.
